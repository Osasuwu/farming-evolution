# Правила ревью

По этим правилам ревьюер оценивает pull request. Читателей два:

- ревьюер в CI (`.github/workflows/code-review.yml`) читает копию из базового коммита PR;
- агент, который перед PR запускает локальное ревью в свежем контексте, читает копию из
  `origin/main`.

Оба читают базовую копию, а не копию из PR: PR, который меняет этот файл, проверяется по тем
правилам, которые он меняет, а его новый текст — часть диффа.

## Для чего ревью

Сборку, юнит-тесты, GameTest и запуск выделенного сервера проверяет `gradlew verify` (проверка
`verify` в CI). То, что ловит она, здесь не повторяется.

Ревью ищет то, для чего нужно суждение: расхождение кода с задачей, ошибки на стыке файлов,
ослабление проверок и происхождение ассетов.

## Как проверять

1. Прочитать заголовок и текст PR, найти связанную задачу (`Closes #N`) и прочитать её условия
   приёмки. Прочитать дифф; изменённые файлы целиком и места вызова — по мере надобности.
2. Оценивать дифф только по классам ниже. Ничего сверх них: ни стиля, ни придирок, ни
   пожеланий на будущее.
3. Термины проекта — в `GLOSSARY.md`, замысел — в `CONCEPT.md`. Незнакомое слово сначала искать
   там.

## Классы находок

- `intent-vs-logic` — код делает не то, что обещают задача или описание PR.
- `requirement-semantics` — условие приёмки связанной задачи на деле не выполнено.
- `regression` — возвращён дефект, который раньше исправили. Перед находкой посмотреть
  `git log` и `git blame` по затронутым строкам.
- `breaking-contract` — смена сигнатуры, формата данных или поведения ломает код вне диффа.
  Перед находкой найти места вызова.
- `exception-handling` — сбой проглочен молча или обработан не так, как требует смысл.
- `concurrency` — гонка или обращение к миру игры не из серверного потока.
- `sidedness` — код, которому нужен клиент (рендер, экраны, ввод), достижим на выделенном
  сервере, или логика сервера выполняется на клиенте.
- `performance` — работа на каждый тик или на каждый блок, которую читатель назвал бы лишней;
  не микрооптимизация.
- `check-weakening` — проверка ослаблена: тест удалён, отключён или его утверждение смягчено,
  расширен список допустимого шума, изменены воркфлоу, хук или этот файл — и при этом PR не
  помечен как правка проверок (`AGENTS.md`, раздел «Правка проверок») либо объяснение в нём не
  сходится с диффом.
- `hollow-test` — добавленный тест не покраснеет, если сломать поведение, в честь которого он
  назван.
- `asset-source` — ассет или заимствованный код без источника и лицензии, производное от
  спрайтов Mojang, декомпилированный код Minecraft (`AGENTS.md`, раздел «Источники ассетов»).
- `design-modularity` — дифф на деле размывает границы модулей; не вкусовое предпочтение.

Имена классов — ещё и схема проверки в CI: `ReviewVerdict` в модуле `checks` принимает ровно
их, а тест `ReviewVerdictTest.classesMatchReviewRules` сверяет два списка.

## Запись результата

Ревьюер в CI пишет результат в файл вердикта и больше никуда. Первая строка — `verdict: clean`
или `verdict: blocking`. При `blocking` дальше идёт по строке на находку:

```
finding: <класс> | <путь>[:<строка>] | <одно предложение: что не так>
```

`blocking` без находок, `clean` с находками, неизвестный класс или любая другая строка —
проверка `review` красная. Чистое ревью — ровно одна строка `verdict: clean`.
